 (1) claudelog.parse must reject records the server would reject (negative usage, any usage > 1e12, empty/oversized ID, missing timestamp) — skip+count them as Skipped with a sanitized warn (project slug only);

 (3) claudelog's batch path, on a PERMANENT error for a chunk, bisects that chunk (send halves) to isolate the bad record(s), records the good ones, logs + drops only the isolated bad record(s) (count them), and then advances the offset. Transient errors keep current behaviour (no advance). Findings:
[SEVERITY high] internal/agent/client.go:164 + internal/claudelog/claudelog.go:252 (record) — Poison pill. The agent treats a permanent 4xx rejection the same as an outage. When the server rejects a batch with 400, the file's offset never advances, so every scan re-sends the same chunk forever with backoff. All valid usage behind the bad record, and anything later appended to that session, is never delivered. Nothing is lost on disk, but delivery stalls indefinitely and the only signal is a warn log. — evidence: agent TestReviewPoisonRecordStallsFile (real control handler: 0 of 3 valid records after 3 scans, 'http 400: records[0]: usage must be non-negative') — minimal fix: (a) in claudelog.parse, skip lines with negative or implausible usage; (b) in RemoteLedger.RecordBatch, on a 400 for a multi-record chunk, bisect or send records singly and drop or quarantine (log id only) the records that get 4xx, so the file can advance; alternatively ingest could return per-record rejects and accept the rest.

[SEVERITY medium] internal/control/ingest.go:125-129 + internal/ledger/ledger.go:318 — Usage is only checked to be >= 0. Two ingested rows near MaxInt64 make SQLite's SUM() fail with 'integer overflow', which breaks Summary for every group (account, host, model, ...) over that range, for ALL accounts. That takes down /control/v1/usage, the widget and the plugin's 24h totals. group=day silently wraps negative in Go (ledger.go:385) instead. Any single ingest host, including a buggy transcript, can do this. — evidence: control TestReviewIngestRejectsImplausibleUsage (200 for MaxInt64); ledger TestReviewSummaryOverflowFromHugeUsage ('SQL logic error: integer overflow') — minimal fix: in ingest, reject any token field above a sane per-record cap (e.g. 1e9) and also check the claudelog sum at claudelog.go:428 for overflow; optionally use TOTAL() in aggCols.

[SEVERITY low] internal/claudelog/claudelog.go:161,186 — Logs leak file paths, against SPEC ('logs never contain ... file paths beyond the project dir name'). The walk warning logs path=<full path>; the scan-file warning logs project=<slug> but err is an *fs.PathError carrying the full session path. The same error is returned from ScanOnce and re-logged by the agent ('agent: usage push failed'). — evidence: claudelog TestReviewScanErrorLogsNoPath (log shows /tmp/.../projects/-home-u-proj/secret-session.jsonl) — minimal fix: unwrap *fs.PathError (like agent.stripPath) before logging or returning, and log projectName(rel) instead of path in the walk callback.
